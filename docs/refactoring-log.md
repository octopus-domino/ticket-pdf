# Журнал работ по Journey

## Фаза 0. Базовый аудит

Зафиксированы пакеты, существующие HTTP-пути, хранение, PDF и компоненты карты. Результаты исходных тестов приведены в [аудите](current-state.md).

## Фаза 1. Модели публикации и снимка маршрута

`JourneyEntity` и `JourneyRoute` перенесены в `domain.model`. Имена JPA-сущностей, таблицы, отображение полей и форматы снимков сохранены. Сервис маршрутов теперь создаёт снимок через конструктор и читает сериализованные данные через метод модели. [Решение о границе хранения](decisions/0002-journey-persistence-boundary.md)

Проверка фазы 1: `mvn clean test`, 315 тестов, 0 ошибок, 6 пропущено.

## Фаза 2. Порты репозиториев

`JourneyStore` и `RouteSnapshotStore` описывают операции сервисов публикации и снимков. Spring Data-адаптеры хранят запросы в `infrastructure.persistence`. Поиск публикаций сохраняет фильтр по владельцу и сайту и порядок `updatedAt DESC, id DESC`. Блокировка удаления, обновления и одноразового использования опирается на исходный запрос с `PESSIMISTIC_WRITE`.

Проверка фазы 2: `mvn clean test`, 315 тестов, 0 ошибок, 6 пропущено.

## Фаза 3. Маршрутизация

Порт `RoadRouter` находится в `domain.service`. Пять реализаций, включая цепочку резервирования, находятся в `infrastructure.routing`. Существующий валидатор координат вынесен в `shared.RouteCoordinates`, чтобы хранение снимков и поиск POI могли использовать прежний код ошибки без зависимости от класса BRouter.

Проверка фазы 3: `mvn clean test`, 316 тестов, 0 ошибок, 6 пропущено. Проверка географических квадрантов выделена из интеграционного теста в отдельный тест адаптера.

## Фаза 4. Источники интересных мест

Пакет провайдеров прогулок перенесён в `infrastructure.poi`. Поиск области использует порт `PoiSource` для OSM и Photon; существующие контракты тематической выдачи, Wikimapia и исторических данных сохранены. `AreaSearchCoordinator` вынесен в `application.map`, сохранив общий результат для одинаковых запросов, очередь и лимит параллелизма.

Проверка фазы 4: `mvn clean test`, 316 тестов, 0 ошибок, 6 пропущено. Дополнительно прошли 6 тестов инструмента раздельной публикации.

## Фаза 5. PDF-компоновка

Фабрика документов, макеты, типографика и проекция в шаблоны конструктора перенесены в `infrastructure.pdf`. Изображения пропускаются через существующее представление data URI с теми же байтами и MIME-типом. HTTP-точки входа, форматы и подготовка шаблонов сохранены.

Проверка фазы 5: `mvn clean test`, 316 тестов, 0 ошибок, 6 пропущено.

## Фаза 6. Выдача, печать и управление публикацией

`JourneyConstructorService` отвечает за выдачу одиночных документов и пакетов с прежними транзакциями, порядком получателей и повтором при коллизии короткого кода. `JourneyPrintService` отвечает за PDF, PDF/A и ZIP с общей блокировкой подготовки и прежними ограничениями архива. Контроллер печати строит HTTP-ответы и передаёт разрешённые пакеты сервису.

`JourneyService` сохраняет имя и вложенные DTO для действующих вызовов. Он ведёт чтение, обновление, статусы и управление публикациями, а создание делегирует конструктору. Общие проверки и сериализация вынесены в `JourneyPublicationData`.

Проверка фазы 6: полный `mvn test`, 316 тестов, 0 ошибок, 6 пропущено.

## Фаза 7. Модель v2 и преобразование старых снимков

Добавлена серверная модель `Trip` с отдельными городами, днями, активностями, переездами, проживанием, документами и бюджетом. Режим `TRIP` проверяет диапазон от двух календарных дней. `TripV1Migration` преобразует ранее сохранённую публикацию и снимок маршрута в представление v2. Точки сохраняют порядок, а явно указанные смены города образуют переезды. При неполных исторических данных неизвестные координаты, пояс и дата остаются пустыми. Старые записи и их ссылки доступны в исходном формате.

Под флагом `ENABLE_TRIP_PLANNER` прикладной сервис сначала читает личный черновик v2 по паре «владелец, ID». При отсутствии черновика он проверяет доступ к прежней публикации и строит представление v2 в памяти. Запись выполняется отдельной операцией. Таблица `journey_trip_drafts` добавляется миграцией без очистки исходных данных. Новый HTTP API ещё не подключён, поэтому браузерный черновик продолжает использовать локальное хранилище.

Проверка: 321 тест, 0 ошибок, 6 пропущено. Интеграционный тест подтвердил, что два владельца могут сохранить черновики с одинаковым ID и обновление одного черновика не влияет на другой.

## Фаза 8. Импорт приватной прогулки

`PrivateJourneyReader` принимает уже выбранный пользователем `SharedWalk`. Частный список прогулок по-прежнему читает клиент Journey внутри iframe. Серверный reader проверяет версию, координаты, последовательность участков и суммарный размер геометрии. Дополнительные поля действующего клиентского формата принимаются.

`TripDraftService.importWalk` создаёт черновик v2 с новым ID и признаком `PRIVATE_JOURNEY`. Дата начала задаётся отдельно, дата окончания по умолчанию наступает на следующий день. Конвертер сохраняет порядок, заметки, ссылки, расстояния и время прохождения в первом дне. Когда в передаче отсутствуют города, используется выбранный пользователем город. Исходная прогулка остаётся в клиенте, а серверное сохранение требует отдельного вызова.

Локальный импорт через iframe и ссылку уже работает в конструкторе. Подключение браузера к серверной операции относится к новому HTTP API. Показ нескольких прогулок на общей карте входит в фазу 9.

Проверка фазы 8: `mvn clean test`, 324 теста, 0 ошибок, 6 пропущено.

## Фаза 9. Выделение области на карте

Под флагом `ENABLE_TRIP_PLANNER` запрос `POST /api/journeys/routes/places/map/selection` принимает круг, прямоугольник или полигон. Сервис поиска получает описывающую окружность, а JTS проверяет включение мест в границы полигона или прямоугольника. Круг использует расстояние по сфере. Пустые, вырожденные, самопересекающиеся и слишком большие области отклоняются до обращения к поставщикам.

Проверки серверного поиска: полный Maven — 326 тестов, 0 ошибок, 6 пропущено. Отдельный прогон проверил три сценария контроллера, включая круг и прямоугольник.

### Проверка границы Journey и CoDoc

В планировщике поездки выбранный день открывает Journey через существующий iframe. Сообщение о завершении проверяется по origin, окну отправителя и каналу. После предпросмотра и подтверждения CoDoc сохраняет готовую прогулку с остановками и геометрией в локальном черновике этого дня. Замена и удаление прогулки доступны целиком. Ранее сохранённые маршруты отображаются с имеющейся геометрией.

Создание пешей линии, точек и поиск мест в прогулке происходят в Journey. Дублирующие инструменты убраны из черновика поездки. Серверный поиск областей остаётся за флагом и сейчас не подключён к этому экрану. Сценарии карты самой поездки, включая города и переезды, требуют отдельной проверки в фазе 9. Подключение серверного сохранения v2, провайдеры расписаний и отелей, сводка, обмен и экспорт остаются в дальнейших фазах.

Проверки границы: 7 целевых тестов фронтенда, `npm run check` и сценарий Playwright с включённым флагом. В браузерном тесте iframe отправляет сообщение в формате Journey. Тест проверяет сохранение выбранного дня после перезагрузки и отсутствие кнопки построения прогулки в планировщике.

## Серверный черновик и расписания

- `PUT /api/trips/{id}` сохраняет v2 от имени текущего пользователя. `GET /api/trips/{id}` читает доступную ему поездку. Ответы имеют `Cache-Control: no-store`. Сохранение в аккаунт выполняется отдельной кнопкой. Обычный импорт готовой прогулки сохраняет данные локально.
- `/trip/{id}` открывает приватную страницу аккаунта с днями, остановками и геометрией прогулки. Маршрут обслуживается SPA и исключён из явных просмотров аналитики.
- `POST /api/journeys/routes/places/trains` принимает коды городов или станций Яндекса и календарную дату. Адаптер хранит ключ в серверной конфигурации, кэширует результаты на час и при сбое может вернуть сохранённый результат с признаком устаревания. Пока интерфейс показывает прямые рейсы по введённым кодам. Выбор рейса как переезда и подбор кодов по названию ещё не подключены. [Контракт Яндекс Расписаний](https://yandex.ru/dev/rasp/doc/ru/reference/schedule-point-point)
- Подтверждённого публичного контракта Ostrovok MCP нет. Официальный Content API требует доступ от поставщика. [Документация Островка](https://docs-api.ostrovok.ru/docs/content-api/)

## Фронтенд, выполненный до последовательного прохода фаз

### Начальный сценарий планировщика

- Фронтенд подключает отдельный черновик в существующем конструкторе поездок. Для локального запуска нужен `VITE_ENABLE_TRIP_PLANNER=true`. При выключенном флаге вход в планировщик скрыт.
- Черновик хранит даты и остановки в браузере. Точки можно добавлять и перетаскивать на карте, переименовывать и удалять в списке. Правки можно отменять и повторять. Сохранение требует двух календарных дней.
- По явному нажатию пешие участки рассчитываются через действующий API маршрутизации и отображаются на карте. В локальный черновик сохраняются остановки и даты.
- Бэкенд читает выключенный по умолчанию флаг `ENABLE_TRIP_PLANNER`. Добавлен доменный тип дат поездки с модульной проверкой. HTTP-операции нового режима пока отсутствуют.

### Импорт прогулки в локальный черновик

- Планировщик принимает готовую прогулку через существующий iframe или ссылку `?walk=`. При передаче из iframe проверяются origin, окно отправителя, канал и схема маршрута.
- Карта показывает точки и геометрию перед подтверждением. Подтверждение копирует прогулку в текущий черновик и может быть отменено из истории правок. Даты поездки пользователь задаёт отдельно. Исходная прогулка остаётся в Journey.
- Локальное сохранение включает геометрию импортированной прогулки. При перемещении, добавлении или удалении остановки геометрия сбрасывается. Черновики прежнего формата читаются без миграции.

### Планы по дням

- Каждый день локального черновика имеет свои остановки, название города и геометрию построенного или импортированного маршрута. Карта и список показывают выбранный день.
- Старый черновик с одним списком остановок открывается как первый день. Новый формат записывается при явном сохранении.
- Дни привязаны к порядковому номеру, поэтому при сдвиге начала поездки планы сдвигаются вместе с ней. Если сокращение поездки оставляет планы за диапазоном дат, эти дни доступны для редактирования, а сохранение требует исправить диапазон или очистить лишние дни.

### Граница Journey и планировщика поездки

- Правка требований отменяет редактор пеших участков внутри нового планировщика. Пользователь открывает Journey из выбранного дня, подтверждает готовую прогулку и получает её точки и линии в локальном черновике. Сохранение в аккаунте требует отдельного нажатия.
- CoDoc ведёт даты, дни, города, проживание и переезды. Точку города можно указать на карте поездки. Карта готовой прогулки используется для предпросмотра и чтения.
- Общая карта доступна в черновике, в сохранённой поездке и по публичной ссылке. Она показывает города с координатами и связывает их пунктиром, когда у переезда отмечены обе стороны. Линейка считает расстояние по прямой и запрашивает автомобильный маршрут только по нажатию кнопки.
- Поиск прямых поездов работает с кодами Яндекс Расписаний. Выбранный поезд сохраняется как переезд с локальными смещениями времени. Ручное проживание входит в сводку и сохраняется в аккаунте вместе с переездами.
- Резервный JSON содержит черновик в формате Trip v2. Публичная страница читает GZIP/base64url из ссылки и фильтрует поля по явной схеме. Для длинных ссылок доступен отдельный файл для отправки без бюджета, документов и данных попутчиков. Его можно открыть через `/trip/view`.
- PDF и ICS доступны владельцу сохранённой поездки. PDF использует общий генератор. ICS формируется через ical4j. Переезды используют локальные смещения при записи и чтении JSON и показываются пунктиром между закреплёнными точками городов.
- В работе остаются справочник городов, подтверждение подключения Ostrovok MCP, завершение карты переездов, пользовательская приёмка и выпуск под флагом.
