# Phase 1.2. Готовность и независимый запуск

Работа опирается на [baseline Phase 1.1b](BASELINE-AFTER.md). На сервере `codoc.site` испытания используют локальный Docker и отдельные project, сеть, БД, volumes и тестовые аккаунты. Приложения поднимаются из собранных JAR. Внешние маршруты изолированы внутренней сетью. Имена и принадлежность Compose-ресурсов проверяются перед остановкой и удалением тестового проекта. Контейнеры production оставались запущены.

| Сигнал | Источник | Что доказывает |
| --- | --- | --- |
| Liveness | Actuator `/actuator/health/liveness` | Процесс способен продолжать работу. Отказ БД не влияет на этот сигнал. |
| Readiness | Actuator `/actuator/health/readiness` | Состояние приложения, соединение с обязательной БД и доступность основных таблиц. Hibernate продолжает проверять полную схему при запуске в режиме `validate`. |
| Dependency health | PostgreSQL по TCP, Redis PING, Gateway workload test | Отдельные сигналы хранилищ и инфраструктуры. |
| Business smoke | Синтетические операции аккаунта, конструктора и маршрутов | Проверяет содержательный контракт и восстановление межсервисных вызовов. |

Document слушает management на `127.0.0.1:9080` в production-профиле. Routing Compose задаёт `127.0.0.1:9093`. Внешний и встроенный Nginx отдают 404 для путей Actuator. Публикация, bootstrap и Compose требуют одновременно HTTP 200 и `{"status":"UP"}`. Скрипт частичной публикации проверяет наличие этого контракта перед изменением контейнера. Переход на readiness требует согласованной сборки JAR и Infra. Откат выполняется парой прежнего образа и прежних Infra-скриптов.

| Участник | Обязательная зависимость | Влияние межсервисного HTTP |
| --- | --- | --- |
| Document | БД Document и рабочее хранилище своего профиля | PDF Account Trip обращается к Routing с лимитами 2 с на соединение и 10 с на чтение. Ошибка транспорта даёт HTTP 503. Конструктор, локальный JWT, публикации и собственный PDF могут стартовать независимо. |
| Routing | БД Routing | Проверка владельца и legacy-проекция используют Document. Конфигурация HTTP ограничивает соединение 2 с и чтение 6 с. При transport exception возвращается 503. У запроса без bearer — 401. |
| Nginx | Собственный конфиг | Маршрутизация использует переменные и DNS resolver на запросе. Отсутствие имени Routing при старте Document допустимо. |
| Gateway | Redis для клиентских ключей | Независим от liveness JVM. Действительное предоставление доступа проверяется отдельно. |

Document читает поездку из Routing. Тот проверяет bearer в Document через `/api/auth/me`. Этот путь повторно входит в Document, но проверка `me` завершается чтением аккаунта и не обращается в Routing. Retry на этом синхронном пути отсутствует. Ошибки и проверенные прогоны собраны в [Failure Mode Analysis](FAILURE-MODE-ANALYSIS.md).

Нормальный rollout сначала проверяет Document, затем отдельно Routing и ingress. Сбой второй стадии фиксируется как ошибка выпуска с сохранением готового Document. Стадия миграции H2 → PostgreSQL сохраняет прежний безопасный отказ после начала импорта.

Воспроизведение в Linux на локальном Docker с загруженными образами:

```bash
python3 ticket-infra/scripts/operational_lab.py --profile h2 --document-jar ./document.jar --routing-jar ./routing.jar
python3 ticket-infra/scripts/operational_lab.py --profile postgres --travel --document-jar ./document.jar --routing-jar ./routing.jar
```

Результаты и ограничения вынесены в [baseline](BASELINE-AFTER.md), [restore drill](BACKUP-RESTORE-DRILL.md) и [измерения ресурсов](RESOURCE-MEASUREMENTS.md).

На сервере подтверждены H2 с выключенным Travel и PostgreSQL/PostGIS с включённым Travel. В обоих прогонах сервисы по отдельности запускались в Docker. H2 с включённым Travel прошёл отдельно на локальных JVM. Для PostgreSQL с выключенным Travel остаётся отдельный runtime-прогон. Проверки HTTP-публикации, создания и восстановления данных использовали только синтетические аккаунты. Production оставался запущен во время испытаний.
