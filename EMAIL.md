# Проверка отправки писем

## SMTP-конфигурация

Используется транспорт `smtp` с явно настроенным SSL/TLS. Для Mail.ru по умолчанию выбран порт 465 и SSL. Противоречивое свойство `mail.transport.protocol=smtps` удалено; авторизация и таймауты теперь настроены для того же транспорта. Отправитель по умолчанию следует за `SMTP_USER`, если отдельно не задан `EMAIL_FROM`.

Рабочий конфиг — `src/main/resources/application.yml`. Файл `src/application.yml` вне каталога ресурсов Maven автоматически не подхватывает.

Настройки передаются **во время запуска backend**, а не как аргументы Docker-сборки:

```dotenv
SMTP_HOST=smtp.mail.ru
SMTP_PORT=465
SMTP_SSL=true
SMTP_TLS=false
SMTP_AUTH=true
SMTP_USER=your-mailbox@example.com
SMTP_PASSWORD=your-app-password
EMAIL_FROM=your-mailbox@example.com
```

Это образец с заглушками. Настоящий пароль приложения задайте в окружении сервера или runtime env-файле вне Git. Не передавайте пароль через `VITE_*`: эти переменные публичны.

Для сервиса на порту 587 с STARTTLS укажите `SMTP_PORT=587`, `SMTP_SSL=false`, `SMTP_TLS=true`. Поддерживается прежний `SMTP_PORT_SSL` как fallback для порта. Таймауты в миллисекундах: `SMTP_CONNECTION_TIMEOUT=10000`, `SMTP_READ_TIMEOUT=30000`, `SMTP_WRITE_TIMEOUT=30000`.

Mail.ru требует разрешённый доступ внешних приложений и пароль приложения: [официальная инструкция](https://help.mail.ru/mail/login/mailer/). Настройки таймаутов: [Spring Boot](https://docs.spring.io/spring-boot/reference/io/email.html).

## Что делает приложение

В production-сборке frontend включён `VITE_FEATURE_EMAIL=true` (также default build-arg Docker). В редакторе есть отдельная кнопка **«Отправить по email»**, которая сразу открывает адресатов, и **«Email-превью»** для проверки письма и скачивания `.eml`. Если флаг задан `false` или пустым через окружение сборки, кнопки скрыты. После изменения флага нужно пересобрать frontend и обновить работающий контейнер.

- В письме используется первый выбранный слайд, отрисованный изображением PNG с CID и текстовой альтернативой. PDF-вложение автоматически не добавляется.
- Адрес отправителя должен быть разрешён SMTP-провайдером. Для ответов на другой адрес используйте Reply-To («Адрес для ответа»).
- После успешного ответа интерфейс пишет «Письмо передано почтовому серверу». SMTP-приём не подтверждает попадание во «Входящие»: возможны задержки, спам-фильтры и последующий отказ доставки.
- Ответ API содержит число принятых и неотправленных писем. Частичный успех и некорректный/пустой отчёт не показываются как полная отправка. Повторный клик во время запроса не запускает вторую отправку.
- Клиент ждёт SMTP batch до 180 секунд вместо общего API-лимита 30 секунд. Это не фоновая очередь; очень большие/медленные рассылки требуют отдельной асинхронной задачи.
- `requestId` сохраняется при повторе того же запроса. Backend пропускает уже подтверждённые отправки; неопределённый исход `PENDING/UNKNOWN` не пересылается автоматически повторно. После обрыва сначала проверьте SMTP-логи, чтобы не продублировать письмо.

## Проверки и границы

Автотесты конфигурации и MIME используют тестовые адреса `example.test` и mock SMTP; внешняя отправка не производится. Тесты UI/API покрывают повтор запроса, защиту от параллельной отправки, частичный отказ и пустой отчёт.

Фактические runtime-переменные и SMTP-логи production-сервера из этой рабочей среды недоступны. Поэтому доставка реального письма и конкретная причина пользовательского сбоя пока не подтверждены. Для диагностики нужны текст ошибки из приложения или серверный лог без паролей.
